## The SEO problem in this specific topic area

> [!warning] Most "local LLM tok/s" content on the web is unverifiable, and a fair amount of it is generated by the exact kind of model it claims to benchmark
> Local-LLM performance is a high-traffic, low-friction topic for content farms: a plausible-looking number, a screenshot of a terminal, zero methodology. Searching for `--n-cpu-moe` or `RX 9070 XT tok/s` surfaces pages with precise-looking figures — "127.4 tok/s!" — that state no quant, no context length, no build hash, no thread count, and no variance. A number with four significant figures and zero reproducibility information is not more credible than a rounder number with a command line attached. It is less.

Before treating any benchmark claim you find online as real, check it against this list:

> [!important] The benchmark-credibility checklist
> 1. **Is there an exact command line?** Not "I ran llama-bench" — the actual flags: model file, quant, `-ngl`, `-ncmoe`, `-fa`, context length, thread count.
> 2. **Is there a variance or repeat-count figure?** A single run of a bandwidth- or thermal-sensitive workload is a data point, not a measurement. `llama-bench` reports std-dev by default — a post that strips it out is a red flag, not a simplification.
> 3. **Is the build identified?** llama.cpp changes fast; a commit hash or release tag matters, especially for anything ROCm/Vulkan-related given how much backend behavior shifts release to release (see the flash-attention and `n-cpu-moe` PRs below).
> 4. **Is the hardware fully specified and plausible?** GPU model *and* VRAM *and* driver/ROCm version *and*, for anything DDR-bound, DIMM population and speed. "Ryzen 9950X + 9070 XT" without DIMM count and configured speed is not enough to reproduce a MoE-offload number, because DDR5 bandwidth is exactly what changes with population (see [[module-0-two-pools]]).
> 5. **Does the claim generalize the way it’s stated?** A number measured at one context length, one quant, and one `n_cpu_moe` value does not transfer to a different combination of the three — and a post that reports one number as "the" throughput for a model is eliding that the roofline is placement-dependent (see the abstract in [[index]]).

If a source fails two or more of these, treat its numbers as directionally suggestive at best, and re-derive your own before relying on them for a configuration decision.

| GBNF grammar format (logit masking for structural validity) | `grammars/` directory in the [ggml-org/llama.cpp](https://github.com/ggml-org/llama.cpp) repository | [[module-10-serving]] |

> [!bug] Gotcha — issue #26663 is model-shape dependent, not a blanket "Vulkan is bad"
> The slowdown is specific to hidden_size ≥ 4096 on gfx1201. A 4B model at hidden_size 2560 shows no such penalty (~183 tok/s), and Vulkan reportedly *beats* HIP on some smaller models. Backend choice in [[module-7-backend-shootout]] is a per-model-shape decision, not a fixed preference — measure both before picking one.

## A note on what’s unverified in this course

Three specific claims in this course are *predictions*, not measurements, until you run the relevant module or capstone: the RX 9070 XT `n_cpu_moe` roofline curve, the AMD `-fa` on/off A/B, and any repo-map-vs-RAG-vs-long-context comparison. See the "Three things nobody has published numbers for" section on [[index]] for exactly what’s missing and which module fills each gap.
